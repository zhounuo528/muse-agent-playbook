# 01 · 连接器接入 SOP

把一个新服务（App / API / MCP / CLI）接进助理能力圈的标准流程。一家一家来，接完一家问用户是否继续下一家。

## 流程五步

1. **先查已连**：查连接器目录与技能目录，该服务已接通就跳过，不要重复施工。
2. **给最省事的接法**：优先级——官方授权链接/扫码 > 官方 MCP > 官方 Skill/CLI > 社区方案（需代码审计）。用户必须亲自申请 Key/授权时，明确告诉他：打开哪个页面、拿什么东西。
3. **凭据入保险库**：密钥只经安全录入通道存入凭据存储，永不在聊天里回显。例外情形（官方工具强制把 Key 写进它自己的配置文件）必须把利害讲清、经用户明确拍板后才许破例，并记录撤销路径（用户在官方控制台重置 Key 即失效）。
4. **真实查询验证**：用一次只读真实查询验收（如查附近门店、查账户积分、查一条真实列表）。查到用户本人的真实数据才算接通；只通了授权页、只列了工具清单都不算。注意查询要打到**核心链路**：一个只验「服务活着」的探针（如查当前日期）不算打通业务链路，验收查询必须返回该服务真正的业务数据（如余票、订单、余额）。
5. **落档成技能**：写连接器文档（端点、鉴权方式、工具白名单、注意事项）＋一份使用技能（什么能直接用、什么动作必须先经用户确认）。下次任何会话读档即会用。

## 验证回执（宣布「已验证」时的最小格式）

每次对用户或在文档里声称「已验证/已接通」，附一份可独立复核的最小回执，缺一不算数：

```
日期 / 验证的命令或查询 / 返回要点（一句） / 退出码或状态 / 版本或 commit（如适用）
```

没有回执的「已验证」只是自述——复核者（含未来的你自己）无从下手，等于没验。

## 铁律

- **付费动作先报价**：下单、打车、订票等要花钱的动作，先列明费用明细，等用户说「确认」再执行。查询类只读动作可直接做。
- **接不上要查清原因再走**：是没个人通道、企业资质墙、功能被官方下线、还是鉴权方式与凭据机制不兼容（如需要用 Key 本身做请求签名、替身机制算不出来）——给出确切原因和证据，再问是否跳到下一家，不许含糊说「接不了」。
- **社区方案先审计**：读代码再安装。重点看：网络请求都发去哪、有没有遥测、有没有碰凭据、删除类操作有哪些。审计结论留档。
- **别承诺未验证的能力**：依赖某个未接通的连接器去安排定时任务，会把任务卡死在依赖上。定时任务只许依赖已验证可用的通道。

## 常见坑

- 官方「有 MCP」不等于个人能用：分清消费侧（查自己的账单/订单）和商户侧（收款/对账）——后者对个人用户是方向相反的产品。
- 文档页顶部的下线/维护通知要逐字看：功能被官方临时下线时，最省事的做法是设一个低频巡检等它恢复，而不是硬装。
- 同一品类留替补：主力＋替补各留一家并写清分工（谁主查、谁核价、谁在故障时顶上），写进两边的文档，不靠记忆。
